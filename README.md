# Avito.Кухня

## Описание проекта

Avito.Кухня — MVP сервиса доставки еды в рамках Авито: площадка даёт пользователям заказывать еду в подключённых заведениях, а заведениям — принимать эти заказы и управлять своим меню.

Репозиторий — два независимых Go-сервиса:
- **`kitchen-api`** — основная площадка: каталог заведений и категорий, оформление и статусы заказов пользователя, кэш меню заведений.
- **`venue-service`** — демонстрационный бэкенд одного заведения: своё меню, приём заказов от площадки, смена статуса заказа персоналом.

Сервисы общаются друг с другом напрямую по HTTP: `kitchen-api` передаёт заказ заведению и получает обратно вебхуки об изменении статуса заказа и меню — подробности и обоснование упрощений в разделе [«Технические решения»](#технические-решения-и-упрощения-mvp) ниже.

## Схема БД

`database-per-service` — у каждого сервиса своя Postgres-база, общих внешних ключей между ними нет. Единственная связь между базами — `kitchen_order_id` в `venue-db`, который просто хранит `orders.id` из `kitchen-db` как значение, без FK (разные СУБД-инстансы, разные сервисы).

**kitchen-db** ([диаграмма](docs/db-schema/kitchen.puml)):
- `categories (id, name)` — справочник категорий кухни.
- `venues (id, name, api_base_url, is_active, created_at)` — заведения, допущенные на площадку; `api_base_url` — адрес их `venue-service`, `is_active` — временно скрыть заведение, не удаляя.
- `venue_categories (venue_id, category_id)` — связь many-to-many между заведениями и категориями.
- `menu_items (id, venue_id, external_id, name, description, price, is_available, removed_at, updated_at)` — **кэш** меню заведения, не источник правды. `external_id` — id этой же позиции в `venue-db`, по нему приходит вебхук синхронизации. `is_available` — временный тумблер («выключить», кончилось на сегодня), `removed_at` — soft delete (товар убран из меню совсем, но строка остаётся ради ссылок из старых заказов).
- `orders (id, venue_id, status, customer_name, customer_phone, delivery_address, comment, created_at, updated_at)` — заказы пользователей; имя/телефон/адрес — гостевой чекаут без аккаунта.
- `order_items (id, order_id, menu_item_id, name_snapshot, price_snapshot, quantity)` — позиции заказа со **снимком** названия/цены на момент оформления, не ссылкой на текущую цену в меню, чтобы история заказа не менялась задним числом при изменении цены.
- `order_status_history (id, order_id, status, changed_at)` — журнал смены статусов заказа.

**venue-db** ([диаграмма](docs/db-schema/venue.puml)):
- `menu_items (id, name, description, price, is_available, removed_at, updated_at)` — своё меню, **источник правды** (тот же паттерн `is_available`/`removed_at`, что и в кэше kitchen-api).
- `orders (id, kitchen_order_id, status, created_at, updated_at)` — заказы, принятые от `kitchen-api`; `kitchen_order_id` (`UNIQUE`) — единственный идентификатор заказа, собственного публичного ID у venue-service нет.
- `order_items (id, order_id, menu_item_id, name_snapshot, price_snapshot, quantity)` — то же самое: снимок названия/цены на момент приёма заказа.

## Технические решения и упрощения MVP

Задание прямо разрешает не делать production-ready решение и просит обосновать упрощения — вот список:

- **Корзины нет как сущности на бэкенде.** Раз нет аккаунтов и сессий, корзина хранится только на стороне клиента; на сервер её содержимое попадает один раз целиком — в теле `POST /orders`. Отдельные "добавить/убрать товар из корзины" ручки не нужны.
- **Только доставка, без самовывоза.** Задание описывает бизнес-задачу именно как "доставку еды" — самовывоз не рассматривался.
- **Оплата только наличными курьеру.** Платёжный шлюз не подключаю — вне скоупа MVP и не влияет на демонстрацию основной бизнес-логики.
- **Отмена заказа ограничена по времени.** Пользователь может отменить заказ только пока статус `создан`/`принят` (до начала готовки) — как только заведение начало готовить, отмена недоступна. Заведение может отменить заказ и во время готовки (закончился ингредиент и т.п.).
- **Меню — soft delete, не hard delete.** Убранный из меню товар помечается `removed_at`, а не удаляется физически — иначе сломались бы ссылки на него из уже оформленных заказов (`order_items`).
- **Кэш меню, а не live-запрос при каждом просмотре.** `kitchen-api` хранит копию меню каждого заведения и синхронизирует её с `venue-service`, а не ходит за меню в реальном времени при каждом открытии страницы. Доступность товара дополнительно перепроверяется в момент оформления заказа (защита от гонки, когда товар пропал уже после того как лежал в корзине).
- **Синхронизация меню — пуш от заведения, а не поллинг.** `venue-service` сам вызывает вебхук `kitchen-api` при любом изменении товара (добавлен/изменён/выключен/убран). `GET /menu` у `venue-service` остаётся только для разовой синхронизации при подключении заведения к площадке, а не как постоянный источник обновлений — иначе пришлось бы опрашивать каждое заведение по расписанию, что не масштабируется при росте числа заведений.
- **Интеграция kitchen-api ↔ venue-service — прямой HTTP (вебхук), без брокера сообщений.** Для одного заведения в рамках MVP брокер (Kafka/RabbitMQ) избыточен — сценария, который оправдал бы такую сложность, здесь нет. Бизнес-логика зависит от абстракции `OrderNotifier`/`MenuSyncNotifier`, а не от HTTP напрямую, так что при реальном масштабировании переход на брокер не затронет сервисный слой.
- **ID заказа передаётся заведению как есть.** Для переписки между `kitchen-api` и `venue-service` используется собственный `UUID` заказа, без отдельного "публичного" идентификатора. UUID v4 непоследователен и неугадываем, поэтому не даёт заведению или третьей стороне оценить объём заказов площадки или подобрать чужой заказ перебором.
- **database-per-service.** У `kitchen-api` и `venue-service` отдельные базы данных без общих внешних ключей — это два независимых сервиса, а не один монолит в двух папках.
- **Доставка — просто статус, без логистики курьера.** `готов → доставляется → доставлен` — это просто смена статуса, без реального курьера, маршрута или трекинга: логистика вне скоупа MVP.

## Стек
- **Go 1.23** — стандартная `net/http` + `ServeMux`, без веб-фреймворка
- **PostgreSQL 16** — своя база на каждый сервис; `pgx/v5` — драйвер, `golang-migrate` — миграции
- **Docker Compose** — оркестрация обоих сервисов и баз
- **OpenAPI 3.0.3** — спецификация API; **Swagger UI** — интерактивная документация
- **PlantUML** — CJM, C4 и ER-диаграммы, все код-генерируемые
- **golangci-lint** (`revive`, `staticcheck`, `gosec`, `errcheck` и др.) — статический анализ
- **air** — hot-reload при разработке; **pgAdmin** — просмотр БД руками

## Запуск

```bash
cp .env.example .env
make up-d
```

Логи:
```bash
make logs
```

Можно и в foreground, без `-d` (`make up`) — тогда логи сразу в терминале. Все команды — в `make help`.

- `kitchen-api` — [http://localhost:8080](http://localhost:8080)
- `venue-service` — [http://localhost:8081](http://localhost:8081)
- `Swagger UI` (обе OpenAPI-спеки, переключатель сверху) — [http://localhost:8082](http://localhost:8082)
- `pgAdmin` (веб-клиент для БД) — [http://localhost:8083](http://localhost:8083)
- Миграции накатываются автоматически при старте каждого сервиса (`migrate ... up && air ...` в `command` соответствующего сервиса в `docker-compose.yml`) — вручную ничего катить не нужно.

## Тесты и линтер

```bash
make lint
```
`golangci-lint` (`revive`, `staticcheck`, `gosec`, `errcheck` и др.) по обоим сервисам, конфиг — `.golangci.yml`.

```bash
make test
```
Юнит- и интеграционные тесты по обоим сервисам. Команда сама поднимает эфемерные тестовые БД (`kitchen-test-db`/`venue-test-db`), прогоняет по ним миграции, запускает тесты и сносит БД после — dev-стек (`make up-d`) при этом не трогается.

## Тестирование ручек

**Swagger UI** — [http://localhost:8082](http://localhost:8082), переключатель `kitchen-api`/`venue-service` вверху страницы, кнопка "Try it out" у каждой ручки. Формы строятся прямо из `api/*.yaml` — какую ручку добавляете в код, такую же дописывайте и в спеку, иначе Swagger UI её не увидит.

**Тестовые данные одной командой:**
```bash
make seed
```
Добавляет в таблицы обеих баз связанные тестовые данные (не просто по одной строке в каждую, а так, чтобы сценарии можно было сразу пощупать):
- **kitchen-db**: 5 категорий кухни, 2 заведения, 6 позиций меню, 2 заказа — один полностью доставлен (со всей историей статусов в `order_status_history`), другой в статусе «готовится».
- **venue-db**: 3 позиции меню (то же первое заведение), 1 заказ, связанный с заказом из kitchen-db через `kitchen_order_id`.

Источники — `scripts/seed/kitchen.sql` и `scripts/seed/venue.sql`. Безопасно гонять повторно — не создаёт дублей. Отдельная команда, не вызывается автоматически при `make up`/`make up-d` — БД должна быть уже поднята и смигрирована.

**pgAdmin** — [http://localhost:8083](http://localhost:8083), для просмотра/редактирования БД руками. Вход сразу без мастера: значения `PGADMIN_EMAIL` / `POSTGRES_PASSWORD` из `.env` (задаются через `PGADMIN_DEFAULT_EMAIL`/`PGADMIN_DEFAULT_PASSWORD` в `docker-compose.yml`; по умолчанию в `.env.example` — `admin@example.com`). После входа — **Add New Server**, подключение (Postgres, хост `kitchen-db` или `venue-db`, порт `5432`, логин/пароль/база — из `.env`) добавляется вручную один раз.
