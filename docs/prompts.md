# Промпты

Ключевые промпты, которыми задавался и правился проект в диалоге с ИИ-агентом (Claude Code) — не полная история переписки, а репрезентативные формулировки по темам, в хронологическом порядке.

## Проектирование: CJM, архитектура, схема БД

-
- Два сервиса в одном репозитории — это два независимых модуля с отдельными базами данных, или один монолит в разных папках? Спроектируй границы между `kitchen-api` и `venue-service`.
- Замени плоскую диаграмму на C4 Container с явными границами систем: клиент, `kitchen-api`, `venue-service` и их базы данных — сейчас не видно, что каждый сервис обращается к своей БД.


## Ручки и бизнес-логика заказов

- Добавь ручку, которой сам `venue-service` сможет проставлять статус заказа — сейчас изменить его может только `kitchen-api`.
- Статус доставки должен двигать только `kitchen-api`, неважно, кто именно инициирует вызов — курьер, крон или вручную. Не привязывай API к конкретному инициатору.
- Не усложняй раньше времени: нужен законченный MVP на реальных сценариях, а не подпорки под гипотетическое будущее.
- Напиши тесты на HTTP-хендлеры для обоих сервисов — сейчас покрыт только сервисный слой.

## Ревью и доработка

- Представь, что ты — senior Go-разработчик, и тебе прислали это тестовое задание на ревью. Перечитай требования из условия задания. Составь три списка: что обязательно должно быть, что желательно, что просто плюс — и проверь каждый пункт по факту. Прогони тесты, потрогай ручки руками, сверь диаграммы с кодом. Отдельно — список недоработок и список того, что реально не работает.
- Реализуй настоящую интеграцию между сервисами вместо заглушек, которые нашлись при ревью. А весь остальной список находок сохрани отдельно у себя, не в репозитории — будем разбирать по одному пункту в следующих сессиях.
- Кто на стороне `venue-service` фактически вызывает смену статуса заказа? — Менеджер заведения, вручную. Зафиксируй это как решённый вопрос.
